## Current release assessment

Talkieo was not ready for App Store submission at audit time. Implementation is now in progress against the gaps below; portal, signing, Sandbox, device, and submission gates still require external verification.

### Ready or reusable

- Xcode 26.6 with iOS SDK 26.5 satisfies Apple's SDK upload minimum that took effect on April 28, 2026.
- The project and Podfile target iOS 15.0.
- The 1024 x 1024 App Store icon exists and has no alpha channel.
- Firebase Core, Authentication, Messaging, Google Sign-In, Meta events, and ATT packages are present.
- User reporting, blocking, moderation history, and admin moderation routes exist and can form the App Review user-generated-content safety baseline.
- Public privacy, terms, and account-deletion pages exist, although their content and behavior need the changes below.

### Blocking gaps

1. **Production identity was inconsistent.** The store-facing brand is locked to `Talkieo`; the existing technical bundle namespace remains `com.techybugs.talkee` to match Android and Firebase.
2. **Firebase is placed but not yet identity-compatible with the current build.** The new plist correctly belongs to `com.techybugs.talkee` and Firebase project `liveapp-8493c`. It will only match at runtime after Runner's bundle ID becomes `com.techybugs.talkee`.
3. **Google Sign-In iOS configuration is incomplete.** Info.plist has no Google reversed-client URL scheme or `GIDClientID`, and `AuthService` is constructed without an iOS client ID. Configure one supported path and test cold-start and returning-user login.
4. **Required privacy permission strings are missing.** The app uses camera, microphone, and photo selection, but Info.plist has no camera, microphone, or photo-library usage descriptions. iOS can terminate access attempts without the required declarations.
5. **Push and Sign in with Apple capabilities are missing.** There is no Runner entitlements file or Runner code-sign-entitlements setting. Add APNs, background remote notification modes, and Sign in with Apple if Google remains a primary login option.
6. **The iOS digital-goods payment path is noncompliant.** Wallet recharge currently requests `gateway: razorpay` and opens Razorpay on every platform. Coins, gifts, themes, entry effects, subscriptions, calls, and games are digital experiences. The iOS build needs StoreKit/In-App Purchase; Android can continue using Razorpay. Port the proven GD Live pattern with Talkee-specific bundle and product IDs instead of copying GD identities.
7. **Account deletion is request-only.** Settings opens a public page/email flow, while the authenticated API has no permanent account deletion endpoint. Implement in-app initiation, server-side deletion/anonymization, token revocation, related-data handling, confirmation, retry/audit behavior, and focused tests.
8. **Signing is not configured.** Runner has no development team setting, this Mac currently reports no valid code-signing identities, and Xcode reports that the locally discovered profiles are invalid because required UUID data is missing. The final `com.techybugs.talkee` App ID, distribution certificate, capabilities, and App Store profile must belong to the intended legal seller team.
9. **The App Store record and business gates are unverified.** Verify bundle ownership, seller/legal entity, agreements, tax/banking status, roles, and whether a Talkieo app record already exists before creating records or accepting agreements. Do not reuse GD Live's bundle ID, products, Firebase project, or App Store record.
10. **Privacy and product metadata need portal mapping.** Update and review the policy for iOS, Firebase/APNs/Apple IAP/Meta/ATT, retention, deletion, live content, and support contacts, then map the actual production data flows to App Privacy answers.
11. **Device-family scope needs a decision.** Runner currently targets iPhone and iPad. Either complete iPad layout/device testing and provide iPad screenshots, or explicitly make the first release iPhone-only before generating store assets.
12. **Dependency risk needs controlled validation.** Several iOS-critical Flutter packages are behind current releases. Do not bulk-upgrade them immediately; upgrade and test Firebase/Auth/Messaging, Google Sign-In, permissions/camera, notifications, WebRTC/LiveKit, StoreKit, and Meta/ATT in focused batches.

## Implementation plan

### Phase 1 - lock product and Apple ownership

1. Use `Talkieo` as the public name everywhere.
2. Confirm the final bundle ID `com.techybugs.talkee` is available to the intended paid Apple Developer team.
3. Confirm the Account Holder/legal seller is correct before accepting Paid Apps agreements or entering tax/banking data.
4. Confirm whether the first release supports iPad or iPhone only.

Acceptance gates:

- The final team can register and provision the exact bundle ID.
- The seller/legal entity is authorized and correct.
- Name and device-family decisions are documented before code-wide identity changes.

### Phase 2 - complete native iOS identity and capabilities

1. Change Runner and RunnerTests bundle IDs to the Talkieo production namespace.
2. Set automatic signing to the authorized team for Debug, Profile, and Release.
3. Add camera, microphone, and photo-library usage descriptions.
4. Add Runner entitlements for APNs and Sign in with Apple; use development APNs for Debug and production for Profile/Release.
5. Add background modes needed for remote notifications and the app's tested call/live behavior.
6. Add the Google client ID and reversed-client URL scheme from the newly placed Talkieo plist.
7. Normalize the chosen app name across Info.plist, launch UI, Flutter title/copy, legal pages, and store metadata.
8. Validate AppIcon and launch assets on light/dark devices and all supported screen sizes.

Acceptance gates:

- Built Runner bundle ID, Firebase plist bundle ID, APNs profile, Google OAuth client, and App Store bundle record all match.
- Google login, Firebase initialization, push registration, camera, microphone, photo selection, ATT, and live audio/video work on a physical iPhone.

### Phase 3 - implement the Apple commerce boundary

1. Port the GD Live StoreKit architecture, changing every identity to Talkieo-specific values.
2. Add the Flutter StoreKit purchase service and select it only on iOS; keep Razorpay Android-only.
3. Add Talkieo backend Apple transaction verification, idempotency, product/coin validation, notification V2 handling, refunds/revocations, and ledger reconciliation.
4. Use the Talkieo technical product namespace `com.techybugs.talkee.coins.{coin_count}` after confirming the exact recharge catalogue.
5. Add production configuration for bundle ID, issuer ID, key ID, private key path, environment, and App Store Server Notifications V2. Never commit the `.p8` private key.
6. Ensure all iOS screens remove or disable external digital-goods payment links and Razorpay checkout.
7. Test Sandbox purchases, interrupted/pending purchases, duplicate callbacks, refund/revocation, zero/partial balances, and server-notification retries.

Acceptance gates:

- iOS exposes only Apple IAP for digital goods; Android behavior remains unchanged.
- Focused backend Apple tests pass and Sandbox purchases credit exactly once.
- Product IDs returned by production APIs exactly match App Store Connect products.

### Phase 4 - compliance, deletion, and review readiness

1. Add authenticated `DELETE /api/account` behavior with a service that safely deletes or anonymizes dependent data and revokes sessions/push tokens.
2. Replace the Settings email/deactivation action with an in-app permanent-deletion confirmation flow; retain the public web page as a fallback.
3. Update privacy policy, terms, deletion page, support contacts, and naming for the iOS release.
4. Verify UGC safeguards end to end: objectionable-content handling, report, block, moderation response, published contact information, and age restriction for mature creator content.
5. Complete App Privacy, age rating, content rights, encryption, advertising identifier, ATT, and export-compliance answers from observed production behavior.
6. Prepare a stable review account and deterministic live-room/recharge review path.

Acceptance gates:

- In-app deletion is independently tested and the public instructions match actual behavior.
- Reviewers can log in, enter a live room, report/block a user, and reach the IAP flow without OTP-only or time-dependent blockers.

### Phase 5 - release validation and App Store handoff

1. Run Flutter analysis and focused tests, then build an unsigned iOS Release to isolate compilation issues.
2. Install a signed Release on a physical iPhone and verify identity, launch, login, permissions, APNs, live audio/video, wallet, IAP, account deletion, and background/foreground recovery.
3. Archive with the exact production bundle ID and Apple Distribution identity.
4. Validate signature, embedded entitlements/profile, version/build, minimum iOS, architectures, included privacy manifests, Firebase plist, symbols, and export output.
5. Create or update the App Store record; add name, subtitle, description, keywords, support/privacy URLs, screenshots for every supported device family, review notes, and IAP review screenshots.
6. Upload to TestFlight, wait for processing, resolve validation warnings, run internal testing, then explicitly approve submission of the app and first IAP products together.

Final release gates:

- Production backend, Apple credentials, notifications, legal pages, and review account are live before upload/submission.
- The uploaded build is processed successfully and selected for the intended version.
- No upload, agreement acceptance, tax/banking entry, or App Review submission occurs without explicit approval from the authorized account holder.
